# Independent Role Records Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the single-role `profiles.role` model with independent Administrator and Teacher business records while preserving Guardian/Student independence, historical teaching attribution, and authenticated account/audit identity.

**Architecture:** `profiles` becomes login identity only. Independent `administrators` and `teachers` tables hold business records; explicit account-link tables grant authenticated Admin/Teacher capability. Teacher-owned data moves from Profile IDs to Teacher IDs. Names/emails never authorize, merge, prohibit, or remove another role.

**Tech Stack:** Next.js 16.3.5, React 19.2.0, TypeScript 5.9.3, Supabase/PostgreSQL 17, RLS/pgTAP, Vitest 5, Playwright 1.63, next-intl 4.13.7, Zod 4.1.11, pnpm 11.19.0.

**Spec:** `docs/superpowers/specs/2026-09-23-independent-role-records-design.md`

## Global Constraints

- Administrator, Teacher, Guardian, and Student are independent business records.
- Duplicate names and business emails are allowed; equality never implies a relationship.
- Supabase Auth email uniqueness applies only to login accounts.
- Teaching assignments/submissions/report sources use Teacher IDs; authenticated actor/audit fields use Profile IDs.
- Production ADMIN-only account must backfill as Administrator-only.
- Existing migrations 1-27 remain immutable; create exactly one migration using `pnpm exec supabase migration new independent_role_records`.
- New public tables have RLS enabled and forced.
- EN/AR and RTL remain supported.
- No hosted production change until local DB/RLS, quality/build, and browser verification pass and production release is explicitly authorized.
- TDD: each task starts RED and ends GREEN.

## Review Focus

1. Existing Auth email reused on a new Teacher: Teacher creation succeeds with no automatic account/Admin mutation.
2. ADMIN-only backfill: Administrator + account link only, never Teacher.
3. Explicit Admin+Teacher: both capabilities coexist and navigate independently.
4. Teacher unlink/deactivation: Admin access and historical Teacher attribution remain intact.
5. Cross-school links: rejected regardless of matching name/email.

- [ ] **Step 4: Implement tables/backfill**

```sql
create table public.administrators(
  id uuid primary key default gen_random_uuid(),
  school_id uuid not null references public.schools(id) on delete restrict,
  display_name text not null check(length(trim(display_name))>0),
  email text check(email is null or (email=lower(trim(email)) and position('@' in email)>1)),
  is_active boolean not null default true,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique(school_id,id)
);

create table public.teachers(
  id uuid primary key default gen_random_uuid(),
  school_id uuid not null references public.schools(id) on delete restrict,
  display_name text not null check(length(trim(display_name))>0),
  email text check(email is null or (email=lower(trim(email)) and position('@' in email)>1)),
  preferred_language public.language_code not null default 'en',
  is_active boolean not null default true,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique(school_id,id)
);

create table public.administrator_accounts(
  school_id uuid not null references public.schools(id) on delete restrict,
  administrator_id uuid not null,
  profile_id uuid not null,
  created_at timestamptz not null default now(),
  primary key(school_id,administrator_id,profile_id),
  foreign key(school_id,administrator_id) references public.administrators(school_id,id) on delete restrict,
  foreign key(school_id,profile_id) references public.profiles(school_id,id) on delete restrict
);

create table public.teacher_accounts(
  school_id uuid not null references public.schools(id) on delete restrict,
  teacher_id uuid not null,
  profile_id uuid not null,
  created_at timestamptz not null default now(),
  primary key(school_id,teacher_id,profile_id),
  foreign key(school_id,teacher_id) references public.teachers(school_id,id) on delete restrict,
  foreign key(school_id,profile_id) references public.profiles(school_id,id) on delete restrict
);
```

No unique business-name/email constraints. Add updated-at triggers. Enable + force RLS on all four.

Backfill with one temporary mapping table so IDs are generated exactly once:

```sql
create temporary table role_profile_backfill(
  profile_id uuid primary key,
  school_id uuid not null,
  legacy_role public.app_role not null,
  role_record_id uuid not null default gen_random_uuid()
) on commit drop;

insert into role_profile_backfill(profile_id,school_id,legacy_role)
select id,school_id,role from public.profiles;
```

Insert Administrator/link rows only for `ADMIN`; Teacher/link rows only for `TEACHER`. Copy Auth email only as initial business data via `auth_user_id`; never map by email.

returns boolean language sql stable security definer set search_path='' as $$
  select exists(
    select 1 from public.profiles p
    join public.administrator_accounts aa on aa.school_id=p.school_id and aa.profile_id=p.id
    join public.administrators a on a.school_id=aa.school_id and a.id=aa.administrator_id

Explicit access algorithm:

```text
1 requireAdministrator
2 load same-school Teacher
3 normalize/validate login email
4 find Auth user
5 if existing profile is another school -> visible cross-school error; do not reuse

7 no Auth user -> invite + create Profile
8 Auth user without Profile -> create same-school Profile
9 insert teacher_accounts idempotently

```
